# Delivery process

## Repository process

- **Trunk-based**: `main` always releasable; short-lived branches (`feat/**`, `fix/**`) or direct commits for solo work; CI green before merge; no long-lived branches.
- **Conventional Commits** with enforced scopes; one commit per complete unit (code + test + docs); the message says _why_ when not obvious.
- **Keep a Changelog** `[Unreleased]` updated in the same commit as the change; **SemVer** tags on release; release notes generated from the changelog.
- **ADRs** (Nygard format: status, context, decision, consequences) for every decision with lasting consequences; new ADR supersedes, never edits an accepted one. Architecture doc updated with the ADR.
- **C4 model** for diagrams: context → container → component; draw.io or mermaid in the repo, regenerated by a make target.
- Docs that must exist: README (quick start < 5 min), conventions, testing, architecture, plan, backlog, runbook (when deployed), screenshots.

## CI/CD

- CI runs exactly `make ci` plus build; cached dependencies; matrix only when it finds real bugs.
- Pipeline order: lint → typecheck → unit → build → e2e → (nightly) load/security scans.
- Deploy as code (Compose, Kustomize, CDK) with a documented rollback; environment config via secrets store; migrations run before the new version serves traffic (expand/contract).
- Feature flags for anything risky; dark launches before announcements.

## DORA four keys (targets for a small team)

| Metric                | Target                                       |
| --------------------- | -------------------------------------------- |
| Deployment frequency  | on demand, at least daily when active        |
| Lead time for changes | < 1 day from commit to prod                  |
| Change failure rate   | < 15 %                                       |
| Time to restore       | < 1 hour (rollback documented and rehearsed) |

2025 DORA: AI amplifies the system you already have; the capabilities that make AI pay off are small batches, fast feedback (tests, CI), clear platform/paved roads, and a healthy data/version-control hygiene. This skill exists to install those.

## Testing strategy (test pyramid, Accelerate)

- Many fast unit tests on the domain; a thin layer of API/component tests with fakes; few e2e journeys that run against the production build; contract tests at service boundaries; a11y and performance checks automated.
- Tests are the executable spec: name = sentence; flaky test quarantined the same day with an issue.
- Coverage thresholds enforced (backend ≥ 90 %, web ≥ 80 %) but reviewed for meaning, not chased.

## Working with the agent (what CLAUDE.md enforces)

- Explore → plan → decide → implement → self-review → verify → report; commit at the end of every completed turn when green; never report done without pasted verification.
- Ask only for information only the user has; otherwise decide, state the reason, move on.
- Keep the project memory (`docs/plan.md`, `backlog.md`, ADRs) current so the next session starts from the repo, not from chat history.
